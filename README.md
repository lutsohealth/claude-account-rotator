# Claude account rotator

A [Claude Code](https://code.claude.com) mod for people with more than one Claude account. It shows each account's usage under the prompt, and moves your session to another account before the one in use runs out.

![The footer up close as the account in use runs low; the session moves to another account and a notice says so; then the panel switches the footer's top row between bars, pies and braille](demo/demo.gif)

<sub>A real session fed imitated accounts (`demo/harness`), so no real account appears.</sub>

## Install

```
/plugin install account-rotator --marketplace ivokund/claude-account-rotator
```

**Turn on auto-update**, or you stay on the version you installed: in `/plugin`, open **Marketplaces**, pick **claude-account-rotator** and choose **Enable auto-update**. Claude Code then updates the mod each time it starts. It is off by default for every marketplace but Anthropic's own.

Then click the usage in the footer, press **+ Add an account** and approve the sign-in in your browser. The account you are signed in with now stays listed as Claude Code's login.

To update by hand instead, pull the marketplace, then the mod, and start a new session:

```
claude plugin marketplace update claude-account-rotator
claude plugin update account-rotator@claude-account-rotator
```

The [changelog](CHANGELOG.md) says what each version changed.

## The footer

A column per account. The top row is the room it has right now (its 5-hour window, or none once its week is spent), the bottom row its week: green with plenty left, red with little. The percents are the account in use's. An account shows a 5-hour window only where it is known to have one, whatever the **5h limit** row is set to: its usage reported one, or a stop marked one. One whose usage reports none, such as a verified Ultra account, and one not read yet leave their top place blank and have no 5h row in the panel; with no account known to have a 5-hour window, the top row is left out, unless it is the one row with glyphs to show that an account needs a sign-in, and the panel's **5h limit** row too, unless it is set to **off**. A top row of percents alone shows only while the account in use has 5-hour room to show. The demo shows both rows.

Click it, or type `/accounts`, for the panel (`/accounts` again closes it). Each account opens with two lines, `<email> · <Company> · <Plan>  updated HH:MM`, then `Used <bar> N% Fable used <bar> N%  resets Nd Nh Nm`: the percents are what is used, whatever the footer fills with, each padded to three cells and a dash to a bar's width, a plan with no Fable week keeps those cells blank and **5h** stands as wide as **Used**, so every account's lines line up whatever its plan; a bar is drawn in the warning color once its window is spent (the 5-hour window at 90%, the week at the **Week** setting's line, the Fable week at 95%), and in none while it has room; and the Fable reset shows only where it differs from the week's. A line under the windows says which numbers are no fresh read: `Fable used: kept from a read 5h ago` for a Fable week an earlier read listed that later reads did not, `Used: stop mark 2h ago` for a window a stop marked spent, `Used: read 3h ago` for a read over an hour old; ages are whole hours, then whole days, and a read under an hour old, as every window is while a session reads it, adds no line. A line under the buttons' line shows the 5-hour window where the account has one (**5h –** while the **5h limit** is off). A usage read that failed since the last that worked ends line 1 with its time, **Failed to update**, its cause in brackets (the status the usage or the profile call answered, a usage call that threw, another check that threw), and for a usage read that failed, by an answer or a throw, when it is tried next, as in `18:39 Failed to update (HTTP 429), next try 18:45`, and dims line 2; a narrow panel shortens the cause (`(429)`), then the next try, then the company, the email and the plan, so line 1 never wraps. An account whose token has run out, with no session on it, ends line 1 with **updated HH:MM · idle** (**idle** with no read yet): it is read again once a session refreshes its token. The account a session runs on, its token run out, ends line 1 with **updated HH:MM**, as that session refreshes the token at its next request. An account that needs a sign-in says **⚠ sign in needed**. The buttons stand on a line of their own under the two lines, on every account; on a panel narrower than line 1, the company, then the middle of the email, shorten. The Fable week shows where its usage lists one, on any plan; on Max and Ultra, which have a separate weekly limit for Fable, **Fable –** while none does, as the week is unknown. The company shows unless the organization is the one named for its own email; the plan by name (Ultra, Max, Pro, Team, Enterprise): the name the account's profile gives, else, on a Max plan, its sign-in's tier, else its plan, with a Max whose usage reports no 5-hour window counted as Ultra; a new sign-in on an account drops the last one's plan, and a sign-in as another account its usage too, and is read at once; **Sign in**, **Use now** and **Remove**, **+ Add an account**, **Rotate now**, **Chrome**, which picks the account Claude in Chrome uses, **Usage based rotation**, which picks the account the rotation moves to, and **Display**, which picks the footer's look:

## What it does

- **Rotates.** Once the account in use is down to 10% of its 5-hour window, where its usage reports one, or to the week left its **Week** row sets (0% by default, so only a spent week; **-** and **+** step it from 0 to 99), the session moves to another account, and a notice says which and why. **Usage based rotation** in the panel picks which: by default the one whose 5-hour window, or else week, resets soonest, so room about to refill is used before it does (a window at 0% used counts by its reset time where its usage gives one, as the window runs all the same); else the one with the most room, or the next in the list; or **disabled**, which leaves switching to you. An account whose usage read failed and that has no usage shown is still moved to, after every account that shows room; not one whose sign-in no check has named yet, as it may hold another login. Its **5h limit** row set to **off** counts no account's 5-hour window, so only the week and the Fable week move the session; **where reported**, the default, counts it where the usage reports one.
- **Recovers.** A turn that still hits a usage limit or a rejected sign-in switches accounts and asks Claude to carry on. An account a plain usage limit stopped counts as spent until its 5-hour window resets. One whose usage reports no 5-hour window, such as a verified Ultra account, or one the weekly limit stopped, counts its week spent until the week resets, and never shows a 5-hour window. A turn that dies in the 35 seconds before a switch lands went out on the account being left: nothing is marked on the one moved to, and the turn carries on there once the switch lands, or, while Claude in Chrome connects, once the visit ends; a Fable stop too. The switch can land a moment later still: a Fable stop on the turn the carry-on starts, within 35 seconds of it and before any response shows the switch took, marks nothing on the one moved to where its usage lists the Fable week with room, and carries on once more. One that dies later, before any response shows the switch took, marks the one moved to only until the switch ends: a switch that ends with no such response (it gives up, you switch again, or you quit Claude Code) drops that mark, unless another session has marked the account since; a rejected sign-in there sets it as needing a sign-in on the same terms. A response since the switch that carries one login's week alone makes a later stop that login's: marked there, and the session pointed back to it where it is not the login moved to; a week two logins share makes the stop nobody's. A switch the stop itself makes keeps it, at once or after waiting for a token to refresh. One that hits the Fable week moves only to an account with Fable room, leaves the 5-hour window alone, and with every Fable week spent stays put and says when the next one frees up, in the band and once through the terminal's notice. The week it marked spent stands until its reset, for every session, whatever lower percent a check of the same week reads in the 30 minutes after the stop, as the usage check can lag the stop; a check of that week later than that, reading it below 100%, ends it, and so does a check whose counter fell 5 points or more below the earlier usage check of the same window (never a response stored since) (a usage reset by hand keeps the reset time), or reads 5% or less where there is no earlier read of it: this ends a week mark and a 5-hour mark too, and drops the Fable row kept from before the fall. A check of a new week also ends it, one that began after the stop or resets later, while a check whose week resets sooner than the mark guessed ends it at that reset. A mark another session drops, as when its switch ends unproven, leaves every session at its next look at the store. A session that never hits the Fable week never leaves an account for it. After a Fable switch to a login whose usage was read 35 minutes ago or less and lists the Fable week with room, the line it sends is `fable-continue-text` in the mod's store, up to 500 characters, sent as your own words; else the mod's own line. After any other Fable pick (an older read, none, one that lists no Fable week, or a login believed spent and tried in case it was reset or freed elsewhere) the line is the mod's own, and says which: how old the read was, or until when the login was believed spent. `account-rotator continue-text` (under [From a shell](#from-a-shell)) sets or clears it. Every other switch sends the mod's own line. A switch held back for a token about to refresh, of any stop, carries on once it lands; so does one whose read of that token gets no answer in 10 seconds, which is tried again each minute. Only a rejected sign-in a stop saw, or a refresh, ends that hold at the token's expiry; a check's mark does not. A stop whose own read of the account fails, its stored sign-in, usage or profile read unanswered (a read with no answer in 10 seconds counts as unanswered, so it never holds a later stop or the resume) or a store write refused, still marks the account, moves and carries on (`stop read failed` in the stop-log); the limit: a fault in Claude Code's own store or hooks outside that read, other than in the terminal's notice, ends the stop's recovery, and the stop-log says `stop handling failed`. A terminal notice that gets no answer, or that Claude Code refuses, holds no stop and ends none. A usage-limit stop with no login left to move to (every login tried, or none with room) says so once, as a notice and in the stop-log (`no login left: one carry-on at <time>`, or `once a login frees up` with no reset time known), and the session carries on by itself once one frees up: after a switch to the one freed, or, on the account in use, 3 minutes after its reset and only if no turn began since the stop (Claude Code may carry on by itself there; after a reload of the mod's code, since the reload), its line then saying that account's limit reset. An account is freed once each of its spent limits (its 5-hour window, its week) reaches its reset time, even when no usage read has worked since. A second stop before then adds nothing. A switch you make before then ends the wait, and nothing is carried on for that stop; so does a later stop's own move, whose own carry-on is the one that goes. A carry-on that went, or a wait that a switch ended, is not owed again after a reload of the mod's code, even where Claude Code refused the write that clears it; it is owed once more where Claude Code refused the mod's store write or read too, where the session's Bash calls carry no `$ACCOUNT_ROTATOR_SESSION`, or where Claude Code still refuses that clearing write over 7 days after the carry-on went or the wait ended. While Claude in Chrome connects, the wait holds, and the carry-on goes at the first check after; where Claude in Chrome starts to connect in the moment the carry-on goes, the carry-on runs during that visit, as any turn running then does. So does a visit whose close gives no answer in 30 seconds. Either way, a reload of the mod's code between the failure and the carry-on drops it. Each session writes what its stops did to the mod's store under `stop-log:<session mark>`, the mark being `$ACCOUNT_ROTATOR_SESSION` in that session's Bash calls: its last 200 entries, each `at` and `what`, naming the stop heard and the limit its words name, the login picked and why, the move, the hold or why it stayed, the carry-on's answer (`resolved` or `drop`), a Connect visit that ended with a carry-on owed (`visit ended with a carry-on owed`, or `..., connected` where the visit connected Claude in Chrome too, with its counts), each Escape below, when the resume entered and when the work went on, with logins by id and no token, email or prompt text. - **Shows what is really in use.** If a switch doesn't take, the footer and panel go back to the old account, and the rotation stops trying the other one for that session. Each account shows only its own usage: a response counts for the account in use only when its week resets at that account's time, which each account has of its own, and accounts whose weeks reset together are read from the usage check alone. A sign-in nobody has confirmed as an account gets no usage at all until it is. When an older version of the mod still runs in another session, the line above the prompt says to restart it.
- **Follows `/login`.** `/login` signs in the account the session is on, which after a switch isn't Claude Code's login. The mod checks who each account's sign-in belongs to: one that now holds another account's asks for its own again, and the session moves off it; one signed in as an account not on the list becomes that account.
- **Picks where new sessions start.** **New on** in **Usage based rotation** picks the account a launcher starts new sessions on: the one with the most room, the first with room, the soonest reset, or one account, else the next after it with room; an account with any limit at 0% left is skipped, and so is one whose sign-in Claude Code rejected, until a new sign-in or a usage read that works, and one Claude Code does not count as logged in (at each check, its `claude auth status` exits 1 with authMethod `none`), which says **⚠ sign in needed** until it does. The three rules also pass over an account the rotation would leave at once (its 5-hour window at 90%, or its week down to the **Week** row's line), unless every account with room is past that line. `account-rotator-launch` (on the Bash PATH while the mod is enabled; `--help`) prints that account's slot, so `CLAUDE_SECURESTORAGE_CONFIG_DIR="$(account-rotator-launch)" claude` starts there with no switch at all. A plain `claude` starts on Claude Code's login, unless `bin/account-rotator-claude` is installed as `claude` in a folder ahead of Claude Code's own on PATH: it then starts every plain `claude`, Orca's background actions among them, on that pick, while a session of the mod wrote the store's rows in the last 60 minutes. Where it starts on Claude Code's login for want of a pick, one more line on stderr says that login reads not signed in when its `claude auth status` exits 1 with authMethod `none`; the `claude` still starts, so `/login` stays reachable. A value of `CLAUDE_SECURESTORAGE_CONFIG_DIR` already set wins, an empty one starts on Claude Code's login, and its `--help` is claude's own (the file's docstring holds its rules). To install it, copy it once (`install -m 755 <the installed mod's bin>/account-rotator-claude ~/.claude/accounts/bin/claude`) and put `~/.claude/accounts/bin` first on PATH; to undo, delete that folder. The mod keeps an installed copy current: at a session's start it replaces a copy that differs from its own `bin/account-rotator-claude`, and it never makes a copy or replaces a link.
- **Keeps Claude in Chrome working.** Your Chrome extension answers only the account it is signed in to: press **Try to connect** next to it in the panel's **Chrome** box. Each window connects Claude in Chrome as that account when it opens (or at its first browser call, while that account is near its limit), and the connection stays as the rotation moves the window. When a browser call still finds no browser, the mod reconnects it and tells Claude to carry on. See [Claude in Chrome](#claude-in-chrome).
- **Warns.** When every account is near its limit, a line above the prompt says when the next one frees up. When an account needs signing in again, the same line says so and signs it in with one click. On macOS, once a session, a notice and a line in the panel say when a `.credentials.json` stands in Claude Code's own folder beside the keychain login (it can stop a move back to that login from landing) and give the command that moves it aside; the mod reads only the file's name and time, never its contents.

## Requirements

- macOS, where Claude Code keeps sign-ins in the keychain, or Linux, where it keeps them in files.
- Claude Code 2.1.299 or later, in its fullscreen renderer (`/tui fullscreen`), the only one that passes clicks on: the panel opens with a click.
- Any Mac terminal: Terminal.app, iTerm2, Ghostty, Warp, VS Code; on Linux, one with mouse reporting. In iTerm2 the profile's *Enable mouse reporting* must be on, in tmux `set -g mouse on`, and iTerm2's `tmux -CC` mode can't run fullscreen.
- Claude subscription accounts (tested with Max and Team seats). For sessions that switch, keep your `/login` a personal account, Pro or Max: see [Team and Enterprise accounts](#team-and-enterprise-accounts).

Claude Code's own "You've used N% of your session limit" warning can still show for a minute after a switch: the switch lands within about 35 seconds, and warnings Claude Code queued before it still play. No mod can hide it.

Mods are early access in Claude Code, and this one relies on internals a release can change: where sign-ins are stored, and the usage endpoint behind `/usage`.

## Team and Enterprise accounts

The mod moves between personal accounts and Team or Enterprise seats. But Claude Code stops plugins from switching accounts, for the rest of a session, when:

- **the session started on a Team or Enterprise account**, or
- **plugins reloaded while one was in use**: `/reload-plugins`, or installing, enabling or disabling a plugin (since 2.1.299).

The block comes from a built-in security default that stops plugins you install from changing where Claude Code reads its sign-in. It also runs on any machine with managed settings. The mod tells you when a session is blocked, and marks it in the footer.

Ways around it, best first:

| Way | Rotates | For |
| --- | --- | --- |
| 1. [Start on a personal account](#1-start-on-a-personal-account) | Yes | Anyone with a personal account, Pro or Max |
| 2. [Start on a chosen account](#2-start-on-a-chosen-account) | No: restart Claude to change accounts | When all your accounts are seats |
| 3. [Turn the security default off](#3-turn-the-security-default-off) | Yes, untested | A machine you alone control: read its warning first |

### 1. Start on a personal account

The fix. A session that starts on a personal account can switch, to seats as well. A plain `claude` starts on Claude Code's login, the account whose folder is `~/.claude` itself:

- **`/login` with your personal account (Pro or Max)** in a new session. `/login` changes Claude Code's login only in a session on it; in a session the mod moved, it signs in that account instead. It doesn't unblock the session it runs in: restart Claude after.
- **Add Team seats from the panel**, not `/login`: **+ Add an account**, and **Sign in** to renew.
- **Restart Claude when blocked anyway**, as after a plugin reload on a seat: quit, and run `claude --continue` or `claude --resume` to keep your conversation (or plain `claude`). Each starts on your `/login`. Not `/restart`: it stays on the account in use. In a background session, quit with `/stop`: `/exit` and ← only detach, the session goes on running on the seat, and `claude --resume` opens it again as it was. When the account in use nears its limit in a blocked window, the line above the prompt gives the command.

### 2. Start on a chosen account

Not a fix: a session started on a seat this way still can't switch. It only picks the account: with only seats, start on the one the footer shows with room, and restart Claude on another when it runs low.

```sh
CLAUDE_SECURESTORAGE_CONFIG_DIR="$HOME/.claude/accounts/2" claude --continue
```

`2` is the account's folder number, its `id` in `account-rotator account list --json`; plain `claude` starts on Claude Code's login. Type the path as here, with no `/` at the end and no `~` in quotes: Claude Code and the mod know the account by its exact text, so any other spelling can start signed out, and shows in the panel as a new account. Set it on the command, not with `export`, or every later `claude` in that shell starts there too. Numbers are reused after **Remove**: check `account list --json` before putting one in an alias.

Started this way on a personal account, a session rotates as in 1, with your `/login` left a seat.

### 3. Turn the security default off

> [!WARNING]
> This removes a security protection for every plugin and every session on the machine. With it off, a plugin you install can override what an organization's policy sets for Claude Code (its hooks, prompt content, settings, tool and MCP server rules) and change where Claude Code reads sign-ins and settings from. Anthropic's [Usage Policy](https://www.anthropic.com/legal/aup) forbids intentionally bypassing restrictions or guardrails built into its products. This is a setting Claude Code offers administrators, but using it so a Team session can switch accounts may count as bypassing. Do it only on a machine you alone control, with plugins you trust. Never do it where an organization manages Claude Code, or where your Team or Enterprise organization's rules forbid it.

Managed settings decide whether the default runs: once they set `prependPlugins`, it runs only if listed there. The file must be owned by an administrator, since Claude Code ignores this key in a file your account can write. If the file below already exists, it holds your organization's policy: leave it alone. Otherwise:

```sh
# macOS
sudo mkdir -p "/Library/Application Support/ClaudeCode"
echo '{ "prependPlugins": [] }' | sudo tee "/Library/Application Support/ClaudeCode/managed-settings.json"

# Linux
sudo mkdir -p /etc/claude-code
echo '{ "prependPlugins": [] }' | sudo tee /etc/claude-code/managed-settings.json
```

It applies to sessions started after. Delete the file to turn the default back on. Managed settings an organization sends from Anthropic's servers can override it.

Untested: this follows how Claude Code 2.1.301 describes and reads the setting, but it has not been tried end to end, and a release can change it. You use it at your own risk.

## Claude in Chrome

The Claude extension in Chrome is signed in to one claude.ai account and answers only Claude Code connections made as that account. Claude Code connects Claude in Chrome at a session's first browser call, as the account the session is on then, and keeps that connection until it drops. With the rotation moving sessions between accounts, that is often not the extension's: Claude Code then says the extension is signed in to a different account and suggests `/login`, which doesn't fix it, and in a session the mod moved signs in the wrong account.

- **Pick the extension's account** in the panel's **Chrome** box. It lists the accounts a Chrome extension answers as: the one this window's Chrome is connected as marked **in use**, the others with **Use for Chrome**. **Other accounts** at the top of the box lists the rest with **Try to connect**, for a Chrome opened on another account; until a browser has answered as any, the box lists them all so. Either press connects Claude in Chrome as that account. Once a browser answers there, that is the account in this window now and in new windows from then on. If none does, Claude in Chrome goes back to the one before, and the account leaves the list until a browser answers as it again. The mod finds out only by connecting, so an account whose Chrome has closed stays listed until it next connects there. With the extension in several Chrome profiles, each signed in to another account, this picks the profile Claude uses.
- **Connected as a window opens.** Claude Code connects Claude in Chrome with the sign-in the window uses, so the mod visits that account: it moves the window there, waits about 35 seconds for Claude Code to read its sign-in, connects by asking Claude in Chrome which browsers answer, and moves the window back. Browser calls wait meanwhile, and a prompt that hits that account's usage limit carries on once the window is back. The connection stays as the rotation moves the window. The window stays put when the rotation would leave that account (its 5-hour window at 90%, or its week down to the **Week** row's line), where a prompt sent during the visit would spend that room or hit its limit, or when no browser answered as it last time while one did as another account: Claude in Chrome then connects at the first browser call, as below. What the **Chrome** box shows of it stands through `/clear`, `/resume` and `/branch`.
- **Reconnects by itself.** After sleep or a network change, the connection comes back as the account in use, and the next browser call finds no browser. The mod visits the extension's account again, runs `/mcp reconnect claude-in-chrome`, and once a browser answers tells Claude to carry on. **Connect** above the prompt does the same by hand. While the window visits the extension's account, its line in the panel says **Connecting Chrome…**, not **in use**. A `list_connected_browsers` call that lists no browser only marks Chrome unpaired: it moves no window, and **Connect** stays a press away.
- **Says what's wrong.** When no Chrome extension answers, the panel and the line above the prompt say so: open Chrome and check its Claude extension is signed in with that account's email; if it is, restart Chrome, which reconnects a stuck extension.

A window Claude Code stops from switching can connect only as the account it is on. Where that isn't the extension's, the line above the prompt gives the command that brings the conversation back in a new session, which starts free to switch: `claude --resume <id>`.

## How it works

- Each account you add gets a folder, `~/.claude/accounts/<n>`: the first number from 2 with no account on it and no folder, by **+ Add an account** and `account add` alike, so a sign-in never replaces the one a folder holds, and removing an account leaves its folder, so neither takes that number again. Claude Code keeps its sign-in in the keychain under that folder's name (on Linux, in that folder's `.credentials.json`), as for any config folder. A switch points the session at another account's sign-in.
- Its only network traffic: each account's usage, from the endpoint `/usage` reads, on one schedule that every session of the installed mod shares, so more sessions add no scheduled reads (a `--plugin-dir` session keeps its own, as under [Develop](#develop)): every 10 minutes for an account some session is using, every 30 for the rest, and at once for a new sign-in. After a failed read every session waits the longer of the endpoint's Retry-After and 2 minutes doubling with each failure, at most an hour, and a new token for the account does not end that wait. An account whose token has run out, with no session on it to refresh the token, is not read: its row says **idle**, and the rotation and **New on** still rank it on its last usage until a session refreshes the token. The mod refreshes no token itself. A session on an older version of the mod keeps a schedule of its own: an account only it has read is read on this one too until that session restarts, though a wait it set still stands. Beside the schedule, a usage-limit stop, `/login` or a sign-in reads the account again once its last read is a minute old and no wait stands, and a switch reads each of the two accounts it moves between at most once while it settles. A stop that has no login left but those believed spent reads each of them once, on the same terms, before it tries one. A Fable stop on the mod's own carry-on reads the account moved to once a switch, however recent its last read, while no wait stands and no other session is reading it. And once per sign-in who it belongs to, from the one Claude Code asks at a sign-in, each with that account's own token. In a session with Claude in Chrome it also asks Claude Code's own Claude in Chrome which browsers answer, as the session opens, before moving off the extension's account, and on **Use for Chrome**, **Try to connect** and **Connect**. Tokens stay where Claude Code keeps them; the mod stores each account's email, organization, plan and last usage, a digest of its token, to tell a new sign-in, and which account your Chrome extension is signed in to.
- Every session also stores each account's row under `rows`, for `account-rotator` (under [From a shell](#from-a-shell)) to read: `<email> · <Company> · <Plan>  updated HH:MM`, then `Used <bar> N% Fable used <bar> N%  resets Nd Nh Nm`, then the 5-hour window's line where the account has one, then the line of numbers that are no fresh read, and each login's week and Fable week as numbers (`windows`: percent, source `read`, `kept` or `stop`, and when it was read or marked), stored with the rows' `v` at 2 under `rows2`, beside `rows` with the lines alone for an older reader, so an older session still running cannot take the numbers away. `updated` is the time of the last usage read that worked, whichever session made it; a usage read that failed since puts its time and `Failed to update (HTTP <status>)` in its place, an account whose token has run out keeps `updated HH:MM` and, with no session on it, adds `· idle`, and an account that needs a sign-in says `⚠ sign in needed`. Each time is stored as an instant, which the reader shows on its own clock and in its own zone, so the stored rows change only when a read, a failure or a reset does. A session looks after each of its usage checks and once a minute, each time from what the store holds, and writes `rows` only when its lines differ from the stored ones, with the time it wrote them: they lag another session's read by at most that minute.

## From a shell

`account-rotator account list` prints each account's row as the panel draws it, then when the rows were written and which account new sessions start on (`--help` says the rest). `--json` prints the envelope of Orca's `orca account list --json`, with the mod's own fields for each account; an account with no row stored has `lines` empty and `hasRow` false. `week` and `fable` give each its percent used, its `source` (`read`, `kept` from an earlier read, or a `stop` mark), `readAt` in epoch milliseconds and `readAgeMinutes` at this clock, each null where the row stored none (a row an older version of the mod stored has none). It reads the mod's store and never writes it. Like `account-rotator-launch`, it is on the Bash tool's PATH while the mod is enabled; in another terminal, run it from the installed mod's `bin` folder, `~/.claude/plugins/cache/claude-account-rotator/account-rotator/<version>/bin/`. Both read the newest store of the installed mod that holds accounts, or the one `--store` names; a newest one that does not parse, as while a session writes it, stops them with exit 1 and its name, so run again.

The rows are as the last session left them: with no session running, each row's `updated` says how old its usage is. A reset that has passed since reads `passed`, and the last line names the account; the usage beside it is as before the reset, where the panel, which reads the account again, would show the new week. A row an older version of the mod stored prints as that version wrote it, its times as of then, and the last line says so.

`account-rotator account select --account <id, email or system>` sets the account new sessions start on, as **New on** in **Usage based rotation** does: `account-rotator-launch` then prints its slot, or the next account's with room where that one has none, and the command says which. It never writes the store either. It leaves a request in the `account-rotator-requests` folder of the store's Claude config folder, naming the store it read; a session of the mod on that store takes it within a minute, and the command waits for its answer (`--wait`, 90 seconds by default, at most 300). With no session running, or when stopped, it takes the request back and exits 3, or 130. A request or answer left behind, by a command killed or a session that died, stays until the next such command on that store removes it, once past the five minutes a request lasts. A `--plugin-dir` session keeps a store of its own, and so does a throwaway config: pass that store with `--store` to reach its sessions.

`account-rotator account use --account <id, email or system>` moves the session running it, as **Use now** does, under the same rule: only an account signed in, and a switch held back while the token in use is about to refresh, in which case the command says so and exits 0. Claude Code's security policy refusing the switch gives its words and exit 4, and so does Claude in Chrome connecting, which moves the session and back, and so does naming the account in use while a switch runs, which may still move the session: run it again in a minute. While a switch waits for that refresh, the panel says so on the row of the account it goes to, and **Use now** waits out Claude in Chrome connecting, with a notice. It finds its session by `ACCOUNT_ROTATOR_SESSION`, a mark the mod sets at its start in the environment of its Bash children; with that unset, as in another terminal, it exits 2. Run in the Bash tool's foreground, it is answered while the command runs. Run any other way, such as `!` at the prompt, under a wrapper's name or as a background Bash, that session takes it within a minute, so a `--wait` under 60 can exit 3. No other session applies a `use`.

`account list --json` names, as `thisSessionAccountId`, the account whose slot that process inherited with the mark, as of when it started: a `list` in the same command line as a `use` reads the account before the move, and a child that outlives its session still names the account it inherited. A command started while Claude in Chrome connects, as it can at a session's start, names the account Chrome connects as.

`account-rotator continue-text --set "<text>"` sets the line a session sends after a Fable switch, as your own words, and `--clear` clears it, so the mod's own line goes: through a session of the mod on the store, as `account select` does, never by writing the store. A text empty or over 500 characters once trimmed (an emoji is one character), or one that is not UTF-8, exits 2 before any request, and a session refuses one too, exit 4. A request file a session cannot read, as one that does not parse or is over 4096 bytes, is answered no, exit 4.

`account-rotator account rm --account <id or email>` signs an account out and drops it, as **Remove** does, through any session of the mod on that store. It keeps every other account, and picks again where new sessions start. A session on that account moves off first; with no other to take over, or while Claude in Chrome connects, it answers no and exits 4. So does an account that holds another login than the command read, or that shares its sign-in with one that stays. It compares only what the command read: where it read no email, whatever login that slot now holds goes; where it read an email and no organization, so does another organization under that email in that slot. A sign-out that fails keeps the account, and says why, for **Remove** too: an account dropped with its login still signed in would be out of sight. Other sessions on that account are not moved: their next check finds its sign-in gone. Claude Code's own login is not the mod's to remove: `rm` exits 2 and names `claude auth logout`.

`account-rotator account add` signs a new account in, as **+ Add an account** does, in that terminal, because a person approves it in the browser: with no terminal, as in the Bash tool, it exits 2. It makes the next free folder, as under [How it works](#how-it-works). Then a session of the mod on that store lists it within a minute, under the folder's number unless another folder's account has that number. A sign-in approved in the browser is not cheap to repeat, so every way out after it keeps the folder and names it: a sign-in that does not finish (exit 5), no session running (exit 3), a session that refuses (exit 4), a folder or store it cannot read or write (exit 1), stopped (exit 130). `account add --folder <path>` asks again: it takes a folder already signed in, and runs no sign-in. A later `add` takes the next number. A login some account already holds, Claude Code's own among them, answers no and exits 4, and its folder stays signed in with no account on it, so the answer gives the sign-out command [TWIN-LEFT-SIGNED-IN]. A row whose organization no session has read yet counts as that login: ask again once a check has read it. `add` checks for a terminal, not a person: anything running in a terminal passes it.

## Uninstall

Remove each account in the panel, which signs it out. Then run `claude plugin marketplace remove claude-account-rotator`, which uninstalls the mod and deletes what it stored, and delete `~/.claude/accounts`.

claude --plugin-dir .     # a session with the mod loaded from this folder
claude plugin validate .
claude plugin test .
python3 -m unittest discover -s tests   # bin/account-rotator and the store pick both bins share

`.github/workflows/checks.yml` runs the last three on every pull request and every push to main.
